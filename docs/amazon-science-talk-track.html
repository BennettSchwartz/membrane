Membrane: Typed, Revisable Memory for Long-Lived Agents

Use this as a guided talk track. The goal is to sound technical and precise without reading a script: explain why flat agent memory is insufficient, then show how Membrane models memory as structured, graph-connected, trust-aware state with lifecycle semantics.

Audience: Amazon Science Length: 30 minutes Tone: research systems, not product pitch Primary APIs: CaptureMemory + RetrieveGraph
0:00-3:00

1. Open With The Failure Mode

Start by saying that most LLM agent memory is still closer to retrieval than learning. A typical system stores chat logs, tool outputs, summaries, or notes, embeds them, and retrieves similar text later. That is useful, but it collapses very different kinds of knowledge into the same object: a raw error log, a durable fact, a temporary task state, and a reusable procedure all become "chunks."

The result is that the agent can remember something similar happened, but it has trouble knowing what kind of thing it remembered, whether it is still true, whether it is safe to reveal, what evidence supports it, and whether it should be replaced by newer evidence.

Flat Memory / RAG Framing

"Find text similar to the current query." The system mostly optimizes recall over stored snippets. Lifecycle, contradiction, trust, and procedural reuse are usually bolted on elsewhere.

Membrane Framing

"Manage memory as typed agent state." The system stores evidence, facts, active state, procedures, entities, and plans with different schemas, policies, and revision rules.

Technical detail to add: in Membrane, the unit of memory is not a text chunk. It is a MemoryRecord with a typed payload, sensitivity, confidence, salience, scope, tags, provenance, graph relations, lifecycle metadata, and an audit log. That record envelope is what enables later policy decisions.

Bridge to next section: "So the project is basically asking: if agents are going to live for days, weeks, or months, what should their memory substrate look like?"
3:00-5:00

2. State The Thesis Clearly

The thesis is that agent memory needs lifecycle semantics. Memory should not just be retrieved; it should be captured, classified, revised, reinforced, decayed, redacted, and eventually pruned when it stops being useful.

Say that Membrane separates remembering from learning. Remembering is capture: preserve evidence from an event, observation, tool call, or task state. Learning is consolidation and revision: decide which patterns become durable facts, procedures, or reusable plans, and update them when outcomes change.

Raw experience The agent observes user requests, tool calls, errors, code changes, outputs, and task outcomes. Say: this is evidence, not yet durable knowledge.
Typed capture CaptureMemory turns that evidence into typed records with source, scope, sensitivity, salience, provenance, and graph links. Say: capture preserves enough structure for later policy decisions.
Consolidation Background jobs scan episodes and promote repeated or useful patterns into semantic facts, competence records, and plan graphs. Say: this is where recall starts becoming learning.
Retrieval RetrieveGraph returns ranked roots plus a bounded neighborhood of connected entities, facts, episodes, procedures, and plans. Say: the output is graph-shaped context, not top-k chunks.
Revision Outcomes can reinforce or penalize records; contradictory evidence can supersede, fork, contest, merge, or retract them. Say: stale memory is handled explicitly, not left as contradictory text.

Research angle: this converts "memory" from a prompt engineering primitive into a systems problem. It introduces testable questions about schemas, promotion criteria, contradiction handling, sensitivity enforcement, forgetting, and long-horizon task improvement.

5:00-10:00

3. Explain The Six Memory Types

Do not present the types as a taxonomy slide and move on. The important point is that each memory type answers a different operational question and therefore deserves different lifecycle rules.

episodic

Raw evidence: tool calls, errors, agent turns, observations, incidents, and outcomes. It answers "what happened?" It should be high fidelity but aggressively decayed.

Technical talking point: episodic records are the evidence substrate. You do not edit an episode to make it semantically correct later; instead, higher-level semantic or competence records are revised while the original episode remains provenance.

working

Resumable state for an active task: current goal, constraints, next actions, open questions, and context summary. It answers "what are we doing right now?"

Technical talking point: this is how an agent can resume without replaying the entire transcript. It stores compact task state with lifecycle rules, so it should disappear or decay when the task is no longer active.

entity

Canonical named things: services, files, repos, projects, people, APIs, databases, tools, incidents, and concepts. Entities form the graph spine.

Technical talking point: entity records let retrieval connect memories around real objects. A service name, repo path, API identifier, or alias can seed graph retrieval even when the exact words in the old episode differ from the current task descriptor.

semantic

Durable but revisable facts and preferences, usually subject-predicate-object style: "auth-service uses Postgres" or "user prefers Go for backend services."

Technical talking point: semantic memory is not a blob summary. The structure makes contradiction handling possible: a new observation can supersede, contest, or fork an older fact instead of creating another untyped paragraph in the vector store.

competence

Procedural knowledge: triggers, recipes, required tools, failure modes, fallbacks, and performance stats. It answers "how do I do this effectively?"

Technical talking point: competence records are the system's hook for procedural learning. They can be scored by applicability, observed success rate, and recency, which gives you a way to ask whether repeated experience actually improves agent behavior.

plan_graph

Reusable action structures: nodes are operations, edges are dependencies. It answers "what sequence or graph of actions solved this class of task?"

Technical talking point: a plan graph preserves topology, not just prose. That matters when a solution has ordering constraints, data dependencies, or checks that should run only after earlier steps succeed.

The record envelope is the real systems move

Every memory type shares a common envelope, and the payload changes by type. This gives you a uniform substrate for retrieval and policy while preserving type-specific semantics.

ID stable record identity

Lets records participate in lineage, graph edges, audit entries, and direct lookup. Without stable IDs, revision becomes "replace text" instead of "preserve a history of state transitions."

Type episodic, working, entity, semantic, competence, plan_graph

Controls the payload schema and lifecycle expectations. This is the main difference from treating all memory as one embedding-ready paragraph.

Sensitivity public, low, medium, high, hyper

Used by retrieval to decide whether the caller receives the full record, only redacted metadata, or nothing. This makes access control part of memory itself.

Confidence how strongly the system believes or trusts the record

Useful for facts, extracted procedures, and selector decisions. You can explain it as epistemic strength separate from current usefulness.

Salience how useful the record is right now

Retrieval can rank by salience when embeddings are absent, and decay/reinforcement update it over time. Confidence says "is this believable"; salience says "should I surface it now."

Scope project, workspace, team, actor, or domain boundary

Prevents a memory from one project from leaking into another. Scoped records are only returned when the caller's trust context includes the scope.

Provenance the evidence chain behind the record

Stores where a fact or procedure came from: source actor, event, tool output, timestamp, or derived episode. This gives you auditability and lets revisions cite evidence.

Relations graph links between records

Edges such as mentions_entity, derived_from, supersedes, supports, or contradicts make retrieval graph-aware instead of only similarity-aware.

Lifecycle decay profile, pinned state, deletion policy

Defines how memory ages. Episodic records can decay quickly, while semantic, competence, entity, and plan graph records have longer lives unless penalized or superseded.

Payload the type-specific structured content

This is where the actual schema lives: episodic timelines, working-state summaries, semantic triples, competence recipes, entity aliases, or plan graph nodes and edges.

Audit Log append-only state transitions

Records creation, reinforcement, supersession, retraction, merge, contestation, and other operations. This matters for explaining why a memory changed.

Interpretation extracted entities, references, or relation candidates

Captures how the system understood the input before or during storage. This is where mention resolution and graph construction become visible rather than hidden in a prompt.

Bridge: "Once you have typed records, you can make ingestion and retrieval much more precise than 'embed this note and hope similarity does the right thing.'"
10:00-14:00

4. Walk Through The Architecture

Use the architecture section to show that this is a concrete implementation, not only an idea. Membrane can run as a long-lived daemon, membraned, over gRPC, or be embedded as a Go library. The same core subsystems are wired under a unified API.

Ingestion Plane Receives CaptureMemory candidates: events, observations, tool outputs, working state, and agent turns. Technical detail: it normalizes the request into one primary MemoryRecord and may create entity or semantic records plus edges.
Policy Plane Classifies memory type and assigns sensitivity, confidence, initial salience, scope behavior, and decay profile. Technical detail: policy separates "what this memory is" from "how long it should live" and "who can retrieve it."
Store Postgres + pgvector stores typed records, JSON payloads, graph edges, audit entries, salience updates, and embeddings. Technical detail: the relational store is authoritative; pgvector is a ranking accelerator, not the source of truth.
Retrieval Plane Runs layered ranking, entity root seeding, trust filtering, and bounded graph expansion for the current task. Technical detail: callers control root_limit, node_limit, edge_limit, and max_hops.
Background Jobs Decay reduces stale salience. Consolidation promotes useful episodes into semantic facts, competence, and plan graphs. Technical detail: learning is asynchronous so raw capture stays cheap and durable promotion can be policy-driven.

Important technical distinction: pgvector is retrieval infrastructure, not the memory model. The authoritative state lives in Postgres tables: record metadata, lifecycle state, graph edges, audit entries, revision history, salience, and confidence. Vector similarity is one ranking signal layered on top of that structured state.

Embedding and LLM services improve ranking and extraction quality on top of the required Postgres + pgvector runtime store. The base tier still supports typed records, graph edges, trust gating, revision history, and decay using that same database substrate.

Slide cue: show one horizontal diagram with CaptureMemory on the left, RetrieveGraph on the right, and Postgres + pgvector as the shared substrate in the middle.
14:00-17:00

5. Explain CaptureMemory

Say that CaptureMemory is the main write API. It accepts arbitrary JSON-compatible content plus metadata describing the source, source kind, scope, sensitivity, tags, summary, context, and reason to remember. The system then stores a typed primary memory record and may create linked entity or semantic records and graph edges.

The key phrasing: CaptureMemory is not just "save this text." It is "submit this experience or observation as a candidate memory into a typed lifecycle system."

The request has a source_kind field. Use that to explain how one API covers several shapes: event, tool_output, observation, working_state, and agent_turn. A tool output usually becomes episodic evidence. An observation with subject, predicate, and object often becomes semantic memory. Working state captures the current thread state.

When interpretation is enabled, capture can resolve entities, create canonical entity records, and materialize graph edges such as mentions_entity, referenced_by, or derived_from. That means the graph is built at write time, not reconstructed only from prompt text at read time.

Bridge: "Once memory is captured this way, retrieval can return context structured around entities, provenance, and graph neighborhoods instead of a bag of similar text."
17:00-21:00

6. Explain RetrieveGraph

This is the second headline API and probably the best place to sound technical. The point is that retrieval returns ranked root memories plus a bounded graph neighborhood. So the output is not just "top-k chunks"; it is task-relevant roots, connected records, edges, and selection diagnostics.

Task Descriptor The caller provides a natural-language task such as "debug auth-service latency after the canary." Technical detail: this descriptor drives embedding search and entity-term lookup; explicit identifiers like repo paths can seed canonical entities.
Trust Context The request includes max sensitivity, authenticated flag, actor ID, and allowed scopes. Technical detail: retrieval fails without trust context, so access control is not an optional wrapper around the API.
Root Ranking The system selects high-signal root records before expanding the graph. Technical detail: ranking can combine salience, pgvector similarity, exact entity matches, relation boosts, and selector scores for competence or plans.
Graph Expansion Membrane walks bounded relation hops from roots to return nearby evidence, entities, facts, procedures, and plans. Technical detail: relation weights and deterministic tie-breaks decide which edges survive when node or edge budgets are tight.
Prompt Context The response contains nodes, edges, root IDs, selector metadata, and non-fatal diagnostics. Technical detail: sensitive records may appear as redacted metadata or be omitted entirely, so the prompt projection is policy-filtered.

Retrieval can use hybrid ranking when embeddings are configured: vector similarity plus salience. Without embeddings, it falls back to salience and deterministic ordering. For competence and plan graph candidates, a selector can score records using applicability, success rate, and recency.

Entity lookup is especially important. A task descriptor can seed retrieval through canonical entity names, aliases, identifiers, and relation evidence. So "debug Project Orchid rollout" can promote a project entity root, then expand to incidents, services, semantic facts, and procedures connected to that entity.

The API also has budget controls: root_limit, node_limit, edge_limit, and max_hops. That matters because agent context windows are limited. Membrane can return a bounded graph neighborhood rather than dumping all memory.

Slide cue: contrast a vertical list of chunks with a small graph: root incident -> auth-service entity -> semantic database fact -> competence procedure -> prior successful plan.
21:00-23:30

7. Revision, Decay, And Forgetting

This is where you distinguish Membrane from normal memory stores. In a long-lived agent, stale memory is not a corner case; it is inevitable. User preferences change, services migrate, procedures stop working, and facts become conditional.

Membrane gives the system explicit revision operations instead of relying on the model to reason over contradictory text snippets. Records can be superseded, forked, retracted, merged, contested, reinforced, or penalized.

Supersede

Use this when newer evidence should replace an older active record. The old record is not erased; the new record links back with lineage so the system can explain what changed and why.

Example to say: "service A uses MySQL" can be superseded by "service A uses Postgres" after a migration, while the audit trail still shows the older belief.

Fork

Use this when the old and new records are both valid under different conditions. Forking prevents the system from flattening contextual exceptions into contradiction.

Example to say: a user may prefer Go for backend services but Python for research notebooks. Both are true with different applicability conditions.

Contest

Use this when evidence conflicts but the system should not decide yet. Contestation makes uncertainty explicit instead of letting two incompatible snippets silently coexist.

Example to say: two incidents disagree about the root cause; the agent can mark the fact contested until a stronger source resolves it.

Retract

Use this when a memory should no longer influence retrieval or behavior, but the system still needs an audit trail that it once existed.

Example to say: a mistakenly captured credential-adjacent note should be removed from active retrieval without destroying the evidence of the retraction operation.

Merge

Use this when multiple records describe the same durable concept and should become one stronger, cleaner record with combined provenance.

Example to say: three repeated observations about an API dependency can merge into one semantic fact supported by multiple episodes.

Reinforce / Penalize

Use these after outcomes. If a retrieved memory helped, reinforcement raises its salience. If it led the agent down the wrong path, penalization lowers future retrieval likelihood.

Example to say: this is how the system gets feedback beyond similarity score. Usefulness becomes state, not just a transient model judgment.

Decay is driven through salience. Records with high salience are more likely to be retrieved. Salience decays over time according to type-specific profiles, and useful records can be reinforced. In the default model, episodic memory decays much faster than semantic, entity, competence, or plan graph memory.

23:30-25:30

8. Competence Learning: The Best Research Hook

Spend real time here. Competence memory is where the project starts to look like learning rather than recall. A competence record stores a procedure: when it applies, what steps to take, what tools it needs, known failure modes, fallback strategies, and performance statistics.

During consolidation, repeated successful episodes with tool graphs can be grouped by tool signature. When a pattern appears enough times, the system can create or reinforce a competence record. That record can later be retrieved for a new task and scored by applicability, observed success rate, and recency.

A good example: if an agent repeatedly fixes a Go test failure by inspecting a package, running a focused test, adjusting a mock, and then running the full suite, that tool pattern can become a competence record. The next time a similar failure appears, the agent can retrieve the procedure instead of rediscovering it from scratch.

Research question to state out loud: "Can we measure whether procedural memory improves agent performance over repeated tasks?" Possible metrics include fewer tool calls, lower latency, fewer repeated failed steps, higher task success rate, and better calibration about when more context is needed.

25:30-27:00

9. Plan Graphs: Memory Meets Orchestration

Plan graphs are related to competence memory but more structural. A competence record can summarize a procedure; a plan graph preserves the action topology. Nodes represent actions or tool invocations. Edges represent data or control dependencies.

n1: inspect logs Identify the failure signature, affected service, request path, or error class. Graph detail: this node produces diagnostic evidence used by later nodes.
n2: run focused test Choose a narrow package, component, or scenario based on the suspected source from n1. Graph detail: this has a control dependency on n1 and a data dependency on the suspected target.
n3: patch mock/config Apply the smallest change suggested by the focused failure: mock expectation, migration, config, or edge-case handling. Graph detail: this node consumes the test output and creates a candidate fix artifact.
n4: run full suite Verify the candidate fix across the broader surface before reinforcing the plan. Graph detail: success increments plan metrics; failure can penalize or fork the plan for a different condition.

Plan graph payloads include a plan ID, version, intent, constraints, input and output schemas, nodes, edges, and metrics such as execution count, failure rate, average latency, and last execution time. Retrieval can select plans based on applicability and past performance.

27:00-28:30

10. Trust-Aware Retrieval

Make the point that useful long-term memory is naturally sensitive. It may contain customer context, credentials-adjacent operational details, private preferences, incident information, or proprietary code facts. If memory is useful enough to guide an agent, it is also worth protecting.

Every record has a sensitivity level: public, low, medium, high, or hyper. Every retrieval request must include a trust context: max sensitivity, authentication state, actor ID, and scopes. Records at or below max sensitivity return fully. Records exactly one level higher may return redacted metadata. Records further above are withheld.

Scopes provide project or actor boundaries. A record scoped to project-auth should only appear when the caller is allowed to see that scope. Unscoped records can remain globally visible subject to sensitivity.

28:30-30:00

11. Evaluation And Honest Maturity Framing

Be careful here. Do not claim the project has solved long-horizon agent evaluation. Say that the repo has capability-oriented evals and regression checks, and that the next scientific step is a longitudinal workload benchmark.

Current eval surfaces

The repo has targeted tests for typed memory behavior, revision invariants, decay and reinforcement, trust-gated retrieval, gRPC request validation, metrics snapshots, vector recall, competence selection, and plan graph selection.

How to frame it: these are capability and regression evals. They prove specific invariants, not a universal claim that long-term agent learning is solved.

Operational checks

The project is broader than a Go package. The verification surface includes Go tests, TypeScript SDK build and tests, Python package checks, OpenClaw bridge tests, docs build, protobuf sync checks, and Postgres-only storage checks.

How to frame it: this is a reference implementation with real client surfaces, not only an RFC.

Next research eval

The stronger study would run repeated agent workloads against several baselines: flat transcript RAG, vector-only memory, semantic-only memory, and the full Membrane stack.

How to frame it: measure whether typed memory reduces repeated mistakes, lowers tool calls, improves task success, and handles drift better over long horizons.

Suggested research metrics: task success rate over repeated tasks, number of tool calls, time to resolution, repeated-error rate, procedure reuse frequency, contradiction rate, memory growth rate, retrieval usefulness, and sensitive-memory leakage rate under different trust contexts.

If asked whether it is production-ready, say: "I would frame it as a serious reference implementation under active hardening, not as a finished managed service. The interesting part for this conversation is the architecture and the testable hypotheses: typed memory, revisability, competence learning, plan reuse, and trust-aware retrieval."

Close / Q&A

12. Closing Claim And Likely Questions

Close with a simple claim: Membrane is interesting because it treats memory as structured agent state with lifecycle semantics, not as more text to stuff into the prompt. Its contribution is not "better embeddings"; it is the integration of storage, retrieval, learning, revision, decay, graph structure, and trust policy into one substrate.

Q: How is this different from RAG?

A: RAG retrieves similar text. Membrane manages typed memory records. It can still use vector similarity, but vectors are only one ranking signal. The core model includes schemas, provenance, revision operations, graph edges, trust gates, salience, and decay.

Q: Where does learning happen?

A: Learning happens through consolidation, reinforcement, and revision. Episodes are captured as evidence; repeated or meaningful patterns can become semantic facts, competence records, or plan graphs. Outcomes can reinforce or penalize those records over time.

Q: How do you avoid memory bloat?

A: Records have salience and decay profiles. Episodic and working memories decay faster. Reinforcement keeps useful records alive; unused or penalized records become less likely to retrieve and can be pruned depending on lifecycle policy.

Q: What would you evaluate next?

A: Longitudinal task performance. Run repeated agent workloads against flat RAG, vector-only memory, semantic-only memory, and Membrane. Measure task success, latency, tool calls, repeated mistakes, memory growth, and leakage under trust constraints.

Q: What is the hardest unsolved problem?

A: Promotion and contradiction policy. Deciding when raw evidence should become durable memory, when a conflict is a true contradiction versus a contextual exception, and when old procedures should be retired are the deep research problems.

Final slide: "From recall to learning: typed memory, graph retrieval, revision, decay, competence, and trust." Keep it simple and leave time for questions.

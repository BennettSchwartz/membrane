---
title: "Decay and Consolidation"
description: "How Membrane keeps memory useful over time through salience decay and background consolidation."
---

Memory becomes less relevant over time. Membrane manages this with two background processes: **decay** reduces the salience of records that haven't been reinforced recently, and **consolidation** extracts durable knowledge from raw episodic traces.

---

## Salience

Every record has a `salience` field in the range `[0.0, 1.0]` (conceptually unbounded, but capped at 1.0 by reinforcement). Salience represents the current importance of a record. Higher-salience records are ranked first in retrieval results.

- New records start with `salience = 1.0`.
- Salience decreases over time via the decay function.
- Salience increases when a record is reinforced.
- Records with `salience < 0.001` and `deletion_policy: auto_prune` are pruned automatically.

---

## Exponential decay

Membrane uses exponential decay with a configurable half-life:

```
new_salience = current_salience × 2^(−elapsed / half_life)
```

Where `elapsed` is the number of seconds since `last_reinforced_at`.

```go
// From pkg/decay/curves.go
func Exponential(currentSalience, elapsedSeconds float64, profile schema.DecayProfile) float64 {
    halfLife := float64(profile.HalfLifeSeconds)
    if halfLife <= 0 {
        return math.Max(currentSalience, profile.MinSalience)
    }
    decayed := currentSalience * math.Exp(-elapsedSeconds*math.Log(2)/halfLife)
    return math.Max(decayed, profile.MinSalience)
}
```

The `MinSalience` field acts as a floor: salience never decays below this value, preventing records from reaching zero unless intentionally retracted or penalized.

### DecayProfile fields

```go
type DecayProfile struct {
    Curve             DecayCurve // exponential (only supported curve)
    HalfLifeSeconds   int64      // time for salience to decay by half (minimum: 1)
    MinSalience       float64    // floor value [0, 1]
    MaxAgeSeconds     int64      // optional maximum age before deletion eligibility
    ReinforcementGain float64    // salience boost per Reinforce call
}
```

The default `HalfLifeSeconds` for new records is `86400` (1 day).

## Reinforce and Penalize

Two operations adjust salience explicitly:

### Reinforce

Boosts salience by `ReinforcementGain`, capped at `1.0`. Updates `last_reinforced_at` and adds a `reinforce` audit entry.

```go
// From pkg/decay/decay.go
func (s *Service) Reinforce(ctx context.Context, id string, actor string, rationale string) error {
    // ...
    gain := record.Lifecycle.Decay.ReinforcementGain
    newSalience := record.Salience + gain
    if newSalience > 1.0 {
        newSalience = 1.0
    }
    // Updates record and adds audit entry
}
```

### Penalize

Reduces salience by a specified amount, floored at `MinSalience`. Adds a `decay` audit entry.

```go
// From pkg/decay/decay.go
func (s *Service) Penalize(ctx context.Context, id string, amount float64, actor string, rationale string) error {
    // ...
    floor := record.Lifecycle.Decay.MinSalience
    newSalience := record.Salience - amount
    if newSalience < floor {
        newSalience = floor
    }
    // Updates salience and adds audit entry
}
```

## Deletion policies

The `deletion_policy` field on each record controls how it may be deleted:

| Policy | Value | Behavior |
|--------|-------|----------|
| Auto-prune | `auto_prune` | Deleted automatically when salience reaches floor (< 0.001) |
| Manual only | `manual_only` | Only deleted by explicit user action |
| Never | `never` | Deletion is prevented entirely |

<Tip>
Set `deletion_policy: never` for records that must persist regardless of salience — for example, pinned user preferences or compliance-relevant facts.
</Tip>

The `pinned` field on `Lifecycle` provides an additional safeguard: pinned records are never decayed or pruned regardless of their deletion policy.

---

## Background decay scheduler

The decay scheduler runs `ApplyDecayAll` at a configurable interval (default: `1h`). After each decay sweep, it runs `Prune` to delete auto-prune records whose salience has reached the floor.

```go
// From pkg/decay/scheduler.go
case <-ticker.C:
    count, err := s.service.ApplyDecayAll(ctx)
    // ...
    pruned, err := s.service.Prune(ctx)
```

```yaml
# config.yaml
decay_interval: "1h"
```

| Job | Default interval | Purpose |
|-----|-----------------|--------|
| Decay | `1h` | Applies time-based salience decay using the exponential curve |
| Pruning | With decay | Deletes records with `auto_prune` policy whose salience has reached 0 |

## Consolidation pipeline

Consolidation promotes raw episodic experience into durable knowledge. The pipeline runs every `6h` by default and consists of five stages:

Derived records retain their source scope and the highest sensitivity of the consumed snapshots and current source records. New evidence can reinforce an existing record only when both its snapshot and current sensitivity meet that record's sensitivity. Lower-sensitivity contributions leave the existing record unchanged; competence aggregation checks each contribution separately. Previously recorded evidence can still raise a derived record's classification without incrementing evidence counts or salience again. These policy checks and promotion audits occur in the write transaction.

Entity resolution uses only same-scope or global entities whose sensitivity is no higher than the derived record. Forward links to those entities are permitted; inverse links require the same scope and sensitivity. When a record is promoted, incompatible known inverse links are removed in the same transaction.

<Steps>
  <Step title="Episodic compression">
    Reduces salience of episodic records that have exceeded their age threshold, making room for new experience.
  </Step>
  <Step title="Structural semantic consolidation">
    Scans episodic records with successful outcomes. For each timeline event with a summary, creates a semantic fact (subject: event kind, predicate: `observed_in`, object: summary). Consolidation reinforces only an existing exact subject-predicate-object fact in the source episode's same scope; a different summary, a different scoped project, or an unscoped global fact is stored separately so scoped evidence does not become globally visible. When entity linking canonicalizes a subject or object to an entity ID, duplicate detection uses the canonical entity-aware fact key across later consolidation runs. Scoped consolidation prefers same-scope entities and then falls back to unscoped global entities, matching capture-time observation behavior. Structured semantic objects are compared by stable JSON, so object field order does not decide whether a fact is a duplicate. Reinforcement appends semantic evidence, provenance, and a `derived_from` graph relation for the newly observed source. Reinforcement is source-idempotent: once an episodic record is recorded as evidence for a fact, later scheduler passes skip that same source/fact pair instead of repeatedly inflating salience.
  </Step>
  <Step title="LLM-backed semantic extraction (Tier 3 only)">
    When `llm_endpoint` and `llm_model` are configured (Postgres + LLM tier), sends episodic summaries to an OpenAI-compatible chat completions API. The LLM extracts structured subject-predicate-object triples that are stored as semantic records.
  </Step>
  <Step title="Competence extraction">
    Groups successful episodic records by their tool signature. Patterns that appear at least twice are promoted into competence records with a recipe derived from the tool sequence. Duplicate detection is scope-aware: an existing competence is reinforced only when both the skill name and derived scope match newly recorded episode evidence.
  </Step>
  <Step title="Plan graph extraction">
    Episodic records with tool graphs containing 3 or more nodes are promoted into plan graph records. Tool nodes become plan nodes; `DependsOn` relationships become control-flow edges. Duplicate prevention inspects existing `derived_from` relations first; if those relations cannot be loaded, consolidation fails closed instead of creating another plan for the same source episode.
  </Step>
</Steps>

```go
// From pkg/consolidation/consolidation.go — RunAll executes all stages in sequence
func (s *Service) RunAll(ctx context.Context) (*ConsolidationResult, error) {
    // 1. Episodic compression
    episodicCount, err := s.episodic.Consolidate(ctx)

    // 2. Structural semantic extraction
    semanticCount, semanticReinforced, err := s.semantic.Consolidate(ctx)

    // 3. LLM-backed semantic extraction (optional)
    if s.extractor != nil {
        extracted, skipped, err := s.extractor.Extract(ctx)
    }

    // 4. Competence extraction
    competenceCount, competenceReinforced, err := s.competence.Consolidate(ctx)

    // 5. Plan graph extraction
    planGraphCount, err := s.plangraph.Consolidate(ctx)

    return result, nil
}
```

### ConsolidationResult fields

```go
type ConsolidationResult struct {
    EpisodicCompressed       int // episodic records whose salience was reduced
    SemanticExtracted        int // new semantic records created structurally
    SemanticTriplesExtracted int // new semantic facts from LLM extraction
    CompetenceExtracted      int // new competence records created
    PlanGraphsExtracted      int // new plan graph records created
    DuplicatesResolved       int // existing records reinforced instead of duplicated
    ExtractionSkipped        int // episodic records that could not be processed
}
```

## LLM-backed semantic extraction

On the Postgres + embeddings + LLM tier (Tier 3), episodic records can be converted into typed semantic facts asynchronously. The extractor sends episodic content to an OpenAI-compatible endpoint:

```go
// System prompt used by the LLM extractor (pkg/consolidation/llm.go)
const semanticExtractorPrompt = "You are a fact extraction system. Given a description "
    + "of an event or experience, extract structured facts as a JSON array of objects "
    + "with exactly three keys: \"subject\", \"predicate\", and \"object\". Extract only "
    + "facts that would be useful to remember across future sessions - persistent "
    + "preferences, learned capabilities, environment facts, and recurring patterns."
```

Each extracted triple becomes a semantic record with `created_by: "consolidation/semantic_extractor"`. Predicates are normalized to lower snake case before de-duplication, so model spellings such as `prefersLanguage`, `Prefers Language`, and `prefers_language` reinforce the same fact. Before insertion, the extractor checks for an existing exact subject-predicate-object fact. It first preserves compatibility with raw triples, then retries using the same entity-canonical subject and object IDs used when new extracted facts are linked into the graph. When an existing fact is reinforced, the extractor records the claimed episodic source as semantic evidence, provenance, and graph lineage in the same transaction as the salience update. It retains the policy of the source snapshot supplied to the LLM and rechecks current source, destination, and entity policy before updating. The queue records the number of unique triples processed, including triples that reinforced existing facts or were skipped because their evidence did not meet the destination's sensitivity.
If any triple in a claimed episode fails to insert or reinforce, Membrane preserves the successful triples but releases the episode claim instead of marking it extracted, so the failed work can retry idempotently.

Configure the LLM endpoint in `config.yaml`:

```yaml
llm_endpoint: "https://api.openai.com/v1/chat/completions"
llm_model: "gpt-5-mini"
# llm_api_key: set via MEMBRANE_LLM_API_KEY environment variable
```

<Note>
Consolidation is automatic and requires no user approval per RFC 15B. All promoted knowledge remains subject to decay and can be revised through explicit operations.
</Note>
